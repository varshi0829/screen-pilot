## 1. Problem statement

On a logged-in GitHub page, when a plan step targets the profile/avatar dropdown
menu ("Click on the profile dropdown menu in the top right corner"), ScreenPilot
highlights a **different** top-right control instead of the avatar button.

Symptom class: `WRONG_ELEMENT_SELECTED` (no longer `ELEMENT_NOT_FOUND`).

Reference avatar markup (supplied):

```html
<button data-login="varshi0829" aria-haspopup="menu">
  <img alt="User avatar">
</button>
```

---

## 2. Audit findings (Phase 8 — analysis only, no code change)

Reproduced the actual `extension/lib/dom-matcher.js` and the verbatim
`collectPageControls()` (`v2-task.js:319-348`) in headless Chromium against a
reconstructed GitHub header. Real `matchElement()` output:

| Target text passed to matcher | Winner | Score | Notes |
|---|---|---|---|
| `"profile dropdown menu"` | **null** | — | zero base-attribute match → gated out at `dom-matcher.js:122-124` |
| `"Profile"` | **null** | — | same |
| `"Create new..."` | Create button | 200 | exact aria-label match |
| `"User avatar"` | Avatar button | 184 | exact img-alt match (`imgAltWeight` 1.4) |

**Two candidate root causes, both code-proven, not yet disambiguated by live logs:**

- **Mechanism A — paraphrase gap.** `SYNONYM_GROUPS` (`dom-matcher.js:18-30`) has no
  profile/account/avatar/user family. If the planner emits a paraphrase
  (`"profile dropdown menu"`), the avatar scores exactly 0 and is *structurally
  unreachable* — type affinity (`aria-haspopup="menu"`) and region bonus are never
  evaluated because they are additive on top of a base match, gated at
  `dom-matcher.js:122-124`.
- **Mechanism B — wrong exact label.** If the vision model copies a wrong-but-exact
  pageControls string (e.g. `"Create new..."`), DOMMatcher correctly scores that
  wrong element 200. This is a vision/prompt issue, not a scoring bug.

**Secondary risk (unconfirmed live):** `collectPageControls()` caps `top_navigation`
at 8 in raw DOM order (`v2-task.js:325,343`) with no ranking. On a real GitHub header
with >8 preceding qualifying elements, the avatar could be truncated before ever
reaching the planner.

## 3. Diagnostic instrumentation (Phase 8.1 — IMPLEMENTED)

To disambiguate Mechanism A vs B, the exact `targetElement` entering the matcher is
now logged.

- **File:** `extension/services/executor-engine.js`
- **Function:** `_resolveElement(step)`
- **Location:** immediately before `this._domMatcher.matchElement(step.targetElement)`

```js
console.log('[SP:Target]', {
  text: step.targetElement?.text,
  type: step.targetElement?.type,
  region: step.targetElement?.region,
  alternatives: step.targetElement?.alternatives
});
```

**Interpretation of the emitted log during the GitHub avatar step:**
- reads `text: "User avatar"` (or synonym-reachable) → **Mechanism B** (planner picked
  a valid-but-wrong label; matcher behaved correctly).
- reads something with no lexical relation to any control's aria-label/alt (e.g.
  `text: "profile dropdown menu"`) → **Mechanism A** (paraphrase gap in
  `SYNONYM_GROUPS`).

Constraints honored: no scoring, matcher, planner, or prompt changes; no refactors.

## 4. Token-budget audit (Phase 8.2 — analysis only, no code change)

OpenRouter 502: *"This request requires more credits, or fewer max_tokens.
You requested up to 4096 tokens. Can only afford 4021."*

All `max_tokens` / `maxOutputTokens` values in the repo:

| Route | File | Function | Line | Value |
|---|---|---|---|---|
| `/api/plan` (Gemini) | `src/app/api/plan/route.ts` | `callGeminiDirect()` | 176 | `4096` |
| `/api/plan` (OpenRouter) | `src/app/api/plan/route.ts` | `callOpenRouter()` | 234 | `4096` |
| `/api/analyze` (Gemini) | `src/app/api/analyze/route.ts` | `POST()` | 196 | `512` (ask) / `2048` (act) |

**Source of 4096:** hardcoded literals, not derived from `maxSteps` or response size.

**Measured planner JSON output** (built from the prompt's own schema example):

| Scenario | JSON size | ~Tokens (4 c/tok) | ~Tokens (3.3 c/tok) |
|---|---|---|---|
| 1-step plan | 981 chars | ~246 | ~298 |
| 10-step plan (maxSteps ceiling) | 5,353 chars | ~1,339 | ~1,623 |

**Recommendation (NOT applied):** set both `plan/route.ts:176` and `:234` to `2048`.
Covers the 10-step worst case (~1,623 tokens) with ~25% headroom, matches the
`/api/analyze` precedent, and resolves the 502 (2048 < 4021 affordable).

## 5. Related observations (audit findings, no changes made)

- **Bundle staleness.** `extension/dist/v2-task.bundle.js` was ~107 lines out of sync
  with source before rebuild. If the loaded unpacked extension is stale, recent
  source fixes (incl. the `#sp-v2-status-banner` self-match filter) may not be active
  in the browser. The self-match filter itself is correct in source
  (`dom-matcher.js:46,429-434`) and loaded unbundled per `manifest.json`.
- **Latency.** No client-side per-stage timers exist in the v2 pipeline; only the
  server-side model-call latency is logged (`plan/route.ts`). The vision model call
  is the dominant cost by inference.
